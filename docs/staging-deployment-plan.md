## Ordered execution plan — not executed

Install locked dependencies without updating lockfiles; review Composer scripts before execution. Run platform requirements, isolated tests and frontend build there. Never use `composer setup`: it generates APP_KEY and runs migrations. Do not use root `composer test`, which clears configuration in this configured production workspace. Review package discovery/cache commands only after staging configuration is installed.
3. **Create isolated infrastructure.** Dedicated database/schema and users, cache/locks, session tables, queue/failed-job namespace, persistent upload roots and mail sink. Use synthetic fixtures only; do not clone customer records or live financial data. No shared production Redis, S3 bucket, storage paths, SMTP credentials, provider secrets or cookies. Review every pending migration and its SQL/side effects explicitly before authorizing application to staging. No blind migrate, rollback or rerun. Keep both November 11 additive migrations in the candidate even though the configured database records them as installed.
5. **Configure staging only.** APP_ENV=staging, APP_DEBUG=false, dedicated HTTPS APP_URL, existing staging key, separate host-only session cookie/name, secure and HttpOnly cookies, reviewed SameSite policy, independent cache prefix and lock-capable persistent cache. Document session encryption policy; current source defaults do not establish target acceptance. Public document root must be `public/`; deny environment/dump/repository/private storage access. Grant service write access only to required storage/cache paths, not application source. Test permissions with the service identity.
6. **Validate infrastructure before workflows.** Test TLS redirect/certificate/renewal, secure cookies, CSRF/session expiry/logout, private proofs and attachments, persistent storage and restart behavior, database grants and absence of production connectivity. 7. **Rehearse services deliberately.** Review `routes/console.php`, queue configuration and all registered schedules. Completion sweeps, GCash reservation expiry, voucher/commerce deadlines and commission reconciliation have side effects. Verify authoritative staging commission enrollment remains disabled; environment flags alone are insufficient. Run only explicitly reviewed jobs against disposable fixtures, then approve a supervisor/service definition, retries, timeouts, failed-job handling, locks, timezone and log rotation. Prevent overlapping workers from another release. Do not blanket-start scheduler or commission jobs.
8. **Prove recovery.** Back up staging DB and linked private files with the existing staging key held securely. Restore into a second independent disposable environment, including generated-column compatibility, consistent data/files, permissions and record/evidence hashes. Verify off-host recovery under a different recovery identity. Do not run the hard-coded verifier unchanged. Record RPO/RTO and responsible operator. 9. **Run acceptance.** Execute the companion checklist with distinct accounts and synthetic parcels, recording screenshots, IDs, before/after state, logs and each PASS/FAIL. Failures block the affected flow; do not repair records to manufacture a pass. Re-run relevant regression suites on the exact built candidate; inherited results are supporting evidence only.
10. **Release decision.** Collect QA, operations, finance/security and release-owner sign-offs with explicit exclusions. Staging acceptance does not authorize production deployment. Any production step requires its separate controlled release decision.

## Migration and rollback restrictions

Existing migration history includes financial default updates, timestamp conversion/data rewriting, generated unique keys, table/field removal and irreversible downs. In particular review `2026_11_06_000003_align_default_rider_pay_rates`, both November 7 Philippine datetime conversions, `2026_10_29_000006_enforce_logistics_company_owner`, and `2026_11_08_000005_add_commission_enrollment_settings`. Do not replay rate changes or timezone conversion. Commission settings must remain disabled. Reconcile missing historical migration sources without deleting/relabeling ledger rows or inventing evidence.

Before any approved staging change, retain a matched DB/private-file/config snapshot and previous built artifact. For code-only rollback, establish schema compatibility first; otherwise restore the matched staging snapshot into the isolated environment. Never rely on automatic `migrate:rollback`: some downs are destructive or intentionally throw. Drain/stop affected workers during a controlled rollback and avoid replaying external side effects. Production recovery remains unverified until separately rehearsed and approved.
